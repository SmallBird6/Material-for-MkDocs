# 基于Iceberg通用湖仓选型

**定位**：一份数据、多引擎共享、生态最开放的通用湖仓

|层|选型|理由|
|---|---|---|
|表格式|Iceberg（v3，CDC 场景开 MoR）|—|
|存储|**MinIO** / S3 / OSS|Iceberg 为对象存储而生，不依赖 rename/list|
|Catalog|**REST Catalog**（Gravitino / Polaris / Nessie）|跨引擎最干净；千万别在对象存储上用 HadoopCatalog|
|批计算|Spark + **dbt**|分层建模、跑 compaction 维护任务|
|流计算|Flink → Iceberg Sink（equality delete）|CDC upsert 入湖|
|交互查询|**Trino**|Iceberg connector 最成熟|
|查询加速|StarRocks（外表直查 / 物化视图）|高并发 serving 层|
|摄入|Flink CDC → Kafka → Flink SQL|—|
|调度|Airflow / DolphinScheduler|—|
|治理/BI|OpenMetadata + Ranger / Superset|—|

**数据流**：业务库 → Flink CDC → Kafka → Flink → Iceberg ODS → dbt/Spark 分层（DWD→DWS→ADS）→ Trino（探索）/ StarRocks（报表）→ Superset

**为什么是最优**：Iceberg 的核心资产是"引擎无关"——Spark 写、Flink 写、Trino 读、StarRocks 读，全靠 manifest 元数据解耦，这套架构把这个优势拉满。REST Catalog 替代 HMS，彻底摆脱 Hadoop 依赖。

**关键坑位**：小文件靠 Spark `rewrite_data_files` 定期合并；快照过期和孤儿文件清理要配定时任务；MoR 表读多写少场景控制 delete file 膨胀

# 基于Paimon流式湖仓选型

**定位**：分钟级新鲜度、主键更新、流批一体的实时数仓

| 层       | 选型                                          | 理由                                    |
| ------- | ------------------------------------------- | ------------------------------------- |
| 表格式     | Paimon（主键表 + LSM）                           | —                                     |
| 存储      | **HDFS**（首选）或 OSS/MinIO + 锁                 | LSM 高频小文件 churn 对 rename/低延迟写最敏感      |
| Catalog | Hive Metastore（存指针 + 借锁）或 FileSystemCatalog | 对象存储部署必须带锁                            |
| 计算      | **Flink SQL**（写入、流读、compaction 全包）          | Paimon 与 Flink 同血缘，流读 changelog 是独家能力 |
| 摄入      | **Flink CDC 整库同步**                          | 自动 schema 演进，上游加列下游自动跟随               |
| OLAP 加速 | **StarRocks / Doris**（Paimon 外表直查）          | 亚秒级 serving，补 Paimon 点查短板             |
| 调度      | Flink 作业常驻 + DolphinScheduler 兜底批任务         | —                                     |
| 治理/BI   | DataHub / Superset                          | —                                     |
**数据流**：MySQL → Flink CDC → Paimon ODS（主键表）→ Flink SQL 流式分层（DWD→DWS，changelog 逐级传递）→ ADS → StarRocks 直查 → BI

**为什么是最优**：Paimon 的 LSM + changelog 让"数仓分层全部用流跑"第一次变得实用——中间层不是 Kafka（不可查、不持久），而是可查、可回溯、带 ACID 的表。分层数据新鲜度从 T+1 压到分钟级，HDFS 则保证高频 compaction 的成本可控。

**关键坑位**：checkpoint 间隔决定 commit 频率，对象存储上建议 ≥1min；流式 join 和维度表用 lookup join + Paimon 主键表；监控 compaction 水位，别让 L0 文件堆积拖垮读性能

# 基于Hudi增量处理数仓

**定位**：频繁 upsert、增量 ETL、存量 Hadoop 体系平滑升级

|层|选型|理由|
|---|---|---|
|表格式|Hudi（更新多选 **MoR**，读多选 CoW）|—|
|存储|**HDFS**|MoR log 依赖 append、timeline 依赖原子 rename，HDFS 是原生土壤|
|Catalog|Hive Metastore（Hive Sync 镜像 schema + 分区）|复用存量 HMS，Hive/Trino/Spark 全认得|
|批计算|**Spark**（写入/compact/clustering/clean 全生命周期）|Hudi 最成熟的引擎绑定|
|摄入|Debezium → Kafka → **DeltaStreamer** / Spark Streaming|官方 CDC 管道，开箱即用|
|交互查询|Trino / Presto（Hudi connector，读优化视图）|—|
|查询加速|StarRocks / Doris 外表，或 ADS 层导出|—|
|调度|Airflow（compaction/clustering 异步任务独立调度）|—|
|治理|Ranger + Atlas（Hadoop 体系原生）|—|

**数据流**：Oracle/MySQL → Debezium → Kafka → DeltaStreamer → Hudi MoR ODS → Spark 增量 ETL（`incremental` 读模式拉变更）→ DWD/DWS → Trino/BI

**为什么是最优**：Hudi 最被低估的能力是**增量处理框架**——下游不再全量重算，而是"给我上次消费之后的变更"，大表 join 成本降一个数量级。MoR + 异步 compaction 把写入延迟压到分钟级，同时整个生命周期（compact/clean/cluster）都在存量 Spark + HDFS 体系内完成，迁移成本最低。

**关键坑位**：MoR 表 compaction 必须独立调度、与写入错峰；多 writer 并发配 ZooKeeper/HMS 锁；timeline 定期 archive 防膨胀；Hive Sync 失败只影响查询注册、不影响数据，重建即可
