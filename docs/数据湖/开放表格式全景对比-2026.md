# 2026 年开放表格式(Open Table Format)全景与详细对比

> 调研时间：2026 年 7 月
>
> **核心结论**:“表格式战争”在 2025–2026 已基本结束——**Apache Iceberg 成为跨厂商的事实标准**,行业竞争的焦点已上移到 **Catalog(目录)层**(Apache Polaris vs Unity Catalog vs Glue Data Catalog)。但学习时不能只学 Iceberg,每种格式代表了不同的架构哲学,值得都理解。

## 一、当前最流行的格式(按 2026 年行业地位排序)

| 格式                 | 最新版本(截至 2026-07) | 定位                | 现状                                           |
| ------------------ | ---------------- | ----------------- | -------------------------------------------- |
| **Apache Iceberg** | 1.11.0 (2026-05) | 通用湖仓表格式           | **事实标准**,所有云厂商/引擎支持                          |
| **Delta Lake**     | 4.3.1 (2026-07)  | Databricks 生态原生格式 | Databricks/Fabric 内首选,靠 UniForm 对外兼容 Iceberg |
| **Apache Hudi**    | 1.2.0 (2026-05)  | 高频 Upsert/CDC     | 稳定但退居第三,保住 upsert 细分市场                       |
| **Apache Paimon**  | 1.4.2 (2026-06)  | 流式湖仓(Flink 原生)    | 中国/流式湖仓生态强势,正向 AI 多模态扩展                      |
| **DuckLake** ⭐     | 1.0 (2026-04)    | 元数据放进 SQL 数据库的新架构 | 2025 年最大黑马,已宣布生产可用                           |
| **Lance**          | 8.0.0 (2026-07)  | 多模态 AI/向量数据格式     | 开辟 AI 数据新赛道,不与上面正面竞争                         |

> **学习优先级建议**:Iceberg(必学)> Delta Lake > Paimon/Hudi(按场景)> DuckLake(了解新架构)> Lance(AI 方向)

## 二、行业大格局(2026 年必须知道的背景)

1. **Iceberg 赢了格式层**:AWS(S3 Tables 原生 Iceberg + Glue)、Google(BigLake Iceberg 表)、Microsoft(Fabric OneLake Iceberg 双向虚拟化)、Snowflake、Databricks(收购 Tabular 后开放 Iceberg REST 接口)、Confluent(Tableflow GA,Kafka 直接物化为 Iceberg)、ClickHouse、StarRocks、Doris…… 全部接入 Iceberg。**Iceberg REST Catalog 已成为行业互操作 API**。
2. **战争上移到 Catalog 层**:Snowflake 把 Polaris 捐给 Apache,并于 **2026-03-05 毕业为 ASF 顶级项目**;Databricks 则以 Unity Catalog + Delta 4.x "catalog-managed tables"(事务协调从文件系统移到 UC)应对。这是当前最热的博弈点。
3. **Iceberg Spec V3 落地**:2026 年的采用前沿。AWS 已全线支持(EMR 7.12+、Glue、S3 Tables),核心特性是**删除向量(Deletion Vectors)+ 行级血缘(Row Lineage)**,社区已开始起草 V4(元数据结构与表示)。
4. **Databricks 双轨制**:对外承诺"走向单一开放标准",实际用 UniForm 让 Delta 表自动生成 Iceberg/Hudi 元数据;但外部引擎对 Databricks 内 Iceberg 仍以只读为主。

## 三、核心技术对比

### 1. 元数据架构(最重要的架构差异)

| 格式 | 架构 | 特点与代价 |
|---|---|---|
| **Iceberg** | 三层文件树:`metadata.json` → manifest list → manifest → 数据文件(Avro 元数据) | 查询规划完全走元数据、无需列目录,可扩展到十亿级文件;依赖外部 Catalog 做原子指针切换 |
| **Delta Lake** | 扁平事务日志 `_delta_log/`(JSON commit 文件 + 每 10 次提交生成 Parquet checkpoint,支持 V2 checkpoint/sidecar) | 自描述、无需 metastore 即可读;但日志重放是经典瓶颈,大表规划慢于 Iceberg |
| **Hudi** | Timeline(每个 instant 有 requested/inflight/completed 三态)+ **内部元数据表**(本身是张 MOR 表,存文件列表/列统计/bloom filter/record index) | 元数据能力最接近数据库,点查/更新定位最精准;架构也最复杂 |
| **Paimon** | **LSM-Tree**:数据文件即 LSM 分层(L0 流式小文件 → compaction 成 sorted run),快照 + manifest | 元数据与主键索引融合,高频流式提交下规划延迟最低,天然吸收小文件 |
| **DuckLake** | **元数据全部是 SQL 数据库里的普通表**(PostgreSQL/SQLite/DuckDB/MySQL/MotherDuck),数据仍是 Parquet | 规划 = 跑 SQL,毫秒级;快照几乎免费;支持跨表 ACID 和事务性 DDL。代价:Catalog 数据库成为中心依赖和写入单点 |
| **Lance** | 每版本一个 manifest + 自带列式文件格式(Parquet 的 AI 替代品) | 提交 = 写单个 manifest,极简;为随机访问/向量索引优化(官方称随机访问比 Parquet 快约 100 倍) |

> 💡 DuckLake 的架构是对 Iceberg/Delta "文件式元数据"的正面批判,是 2025–2026 最有思想冲击力的设计,学习价值很高。

### 2. ACID 与并发模型

| 格式 | 模型 | 提交仲裁者 |
|---|---|---|
| **Iceberg** | 乐观并发(OCC),Catalog 原子换指针;读快照隔离,写经 CAS 可串行化 | Catalog(Glue 锁 / REST / Nessie / JDBC / Hive 锁) |
| **Delta Lake** | MVCC + OCC,put-if-absent;**4.x 起可交给 catalog 协调**(catalog-managed tables) | 对象存储条件写 / DynamoDB / Unity Catalog |
| **Hudi** | OCC + 1.x 非阻塞并发(流式多写) | 可插拔锁(ZooKeeper / HiveMetastore / DynamoDB) |
| **Paimon** | OCC 快照提交,partial-update 合并引擎容忍多流并发写 | 文件系统原子 rename / metastore |
| **DuckLake** | **中心数据库事务**,多表多语句真 ACID,DDL 也在事务内;冲突自动重试 | SQL 数据库本身(语义最强,实现最简单,单点串行) |
| **Lance** | OCC manifest 版本化 | 对象存储条件写 |

### 3. Schema / 分区演进 / 聚簇

- **Iceberg**:按列 ID 的完整 schema 演进(改名/重排/类型扩宽);**隐藏分区 + 真分区演进**(改分区方案不重写数据)——这是它当年击败前辈的杀手特性;V3 新增多参数 transform。
- **Delta Lake**:column mapping 支持不重写改名/删列;**无分区演进**;用 **Liquid Clustering**(`CLUSTER BY`,增量式)同时替代分区和 Z-Order;4.0 GA 类型扩宽。
- **Hudi**:schema 演进完善,分区演进有限;clustering 是一等表服务(linear / z-order / Hilbert / consistent bucket)。
- **Paimon**:bucket + LSM sorted run 天然有序;append 表支持增量 clustering(order / z-order / Hilbert)。
- **DuckLake**:schema 演进 + 类型提升,**暂无隐藏分区/分区演进**(v1.0)。
- **Lance**:**加列/回填列不重写历史数据**(为 ML 特征工程设计),六者中独有。

### 4. 行级操作(UPDATE/DELETE/MERGE)

| 格式 | 模式 | 机制 |
|---|---|---|
| Iceberg V2 | CoW 或 MoR | position delete + equality delete |
| **Iceberg V3** | MoR | **Puffin 文件里的二进制删除向量 + 行血缘**(`_row_id`、`_last_updated_sequence_number`),为高效 MERGE/CDC 铺路;写入侧已在 1.10/1.11 落地,引擎读取支持仍在铺开(ClickHouse、Fabric、Athena 尚不支持 V3 DV) |
| **Delta Lake** | CoW 或 MoR | RoaringBitmap 删除向量(Databricks 默认开启);Trino 可读写 DV |
| **Hudi** | **COW / MOR 按表选择**,upsert 优先设计 | MOR = base Parquet + Avro delta log,读时合并或由 compaction 合并;record-level index 路由更新 |
| **Paimon** | **LSM MoR** | 主键表 + 多种 merge engine(dedup / partial-update / aggregation / first-row)+ changelog producer |
| **DuckLake** | MoR | delete 文件 + 维护期 rewrite files with deletes |
| **Lance** | MoR | fragment + 删除文件,稳定 row ID 供向量索引更新 |

### 5. 时间旅行 / 增量消费

- 全部支持快照时间旅行与回滚(Delta 用 `RESTORE`,Iceberg 用 `rollback` procedure,DuckLake 用 `AT (VERSION => n / TIMESTAMP => t)`)。
- **增量/CDC 是分水岭**:
  - **Delta Lake**:原生 **Change Data Feed**(`_change_data/`,含 insert/update 前后镜像/delete)。
  - **Hudi**:**增量拉取(带前后镜像)是历史最强项**。
  - **Paimon**:流式 changelog 就是主要消费模式(LSM 天然产出 changelog)。
  - **Iceberg**:只有文件级 incremental scan(V3 行血缘在为行级 CDC 打地基)。
  - **DuckLake**:提供 data change feed;快照便宜(只是数据库行),快照过期 + 文件清理由维护命令完成。

### 6. 流式读写

- **Paimon 是流式原生王者**:Flink 两阶段提交、秒级提交、LSM 吸收小文件。典型链路:**Flink CDC → Paimon → StarRocks/Doris/Trino**。
- **Hudi**:Spark/Flink 双写端完善,1.x 支持非阻塞多流并发写。
- **Delta Lake**:Spark Structured Streaming 原生;Flink 连接器已进入维护模式(全面转向 Delta Kernel)。
- **Iceberg**:Flink/Spark 支持完善,但高频提交造成元数据膨胀,实务上多为分钟级微批。
- **DuckLake / Lance**:暂无成熟 Flink/Spark 流式写生态(以 DuckDB/Python/Rust 生态为主)。

### 7. 引擎与厂商生态矩阵(2026 现状)

| 引擎/厂商 | Iceberg | Delta | Hudi | Paimon |
|---|---|---|---|---|
| Spark | 读写(V3 进行中) | **原生** | 读写 | 读写 |
| Flink | 读写(1.11 已能写 V3 DV) | 维护模式 | 读写 | **最佳** |
| Trino | 读写 V2 + 物化视图 | 读写(DV/CDF) | 只读 | 读写 |
| Snowflake | **读写 + Open Catalog(Polaris)** | 经 UniForm | – | – |
| Databricks | 读写(UC Iceberg REST,外部引擎只读) | **原生默认** | 经 UniForm 读 | – |
| AWS(Athena/Glue/EMR/Redshift/S3 Tables) | **全线支持,V3 已上 EMR/Glue/S3 Tables** | 读 | 读写(EMR 内置) | EMR 支持 |
| BigQuery/BigLake | **BigLake Iceberg 托管表** | 读 | – | – |
| MS Fabric | OneLake **Iceberg↔Delta 双向虚拟化**(目前仅 V2) | **原生** | – | – |
| ClickHouse | 读(position/eq delete,不支持 V3 DV) | 读;**25.10 起写入 beta(经 delta-kernel)** | 读 | – |
| StarRocks / Doris | 读写 + 物化视图 + compaction | 读 | 读 | 读(Doris 是 Paimon 常见 serving 层) |
| DuckDB | 读写(iceberg 扩展) | 读(delta 扩展) | – | –(DuckLake 是其原生格式) |

> **一句话总结**:需要跨引擎/跨厂商写入互操作 → 只有 Iceberg;Databricks/Fabric 内部 → Delta;Flink 流式入湖 → Paimon;高频 upsert 且已有 Hudi 资产 → Hudi。

### 8. 表服务(compaction / clustering / 清理)

- **Hudi 内置最完整**:compaction、clustering、clean、index 全是表服务,可 inline / async 运行。
- **Paimon 自动化最好**:LSM compaction 在 sink 内部自动完成(Flink 有专门 compaction coordinator),流式场景几乎零外部工具。
- **Iceberg / Delta 开源版是"半内置"**:Spark procedure(`rewrite_data_files`、`expire_snapshots` 等)/ `OPTIMIZE`、`VACUUM` 都提供,但调度靠外部;或购买托管自动化(Databricks predictive optimization、Tabular、Onehouse、**S3 Tables 自动 compaction**)。
- **DuckLake**:以 SQL 维护命令形式提供(merge files / expire snapshots / cleanup of files / rewrite files with deletes)。
- **Lance**:API 提供(`optimize`、`cleanup_old_versions`),LanceDB Cloud 自动化。

## 四、选型建议(2026)

| 场景 | 推荐 |
|---|---|
| 新建通用湖仓,要跨引擎跨厂商、防锁定 | **Iceberg** + REST Catalog(Polaris / Gravitino) |
| 深度绑定 Databricks 或 Microsoft Fabric | **Delta Lake**(开 UniForm 保出口) |
| Flink 流式入湖、CDC 整库同步、秒级新鲜度 | **Paimon** |
| 超高频 upsert、增量 ETL、已有 Hudi 体系 | **Hudi** |
| 中小规模湖仓、单机/分析团队、追求极简 | **DuckLake**(关注其 Catalog 高可用方案) |
| 向量/多模态/ML 特征数据 | **Lance**(或与 Iceberg 并存,各司其职) |
| 多格式并存的存量迁移 | **Apache XTable**(孵化中,发版慢,优先用各格式自带互操作) |

## 五、学习路径建议

1. **先吃透 Iceberg**:读官方 spec(快照 / manifest / 隐藏分区 / V3 DV 与 row lineage),这是当前行业标准语言。
2. **对比理解 Delta 的事务日志模型**和 catalog-managed tables 的转向——理解"提交协调从文件系统移到 catalog"这个行业趋势。
3. **用 Paimon 学 LSM vs 文件树的流式权衡**;Hudi 理解 timeline + 元数据表 + COW/MOR 选择即可。
4. **读 DuckDB 团队 2025-05 的 DuckLake 发布博客**——它是对过去十年文件式元数据最好的反思文章。
5. **动手实验**:MinIO + Polaris + Spark/Flink + Iceberg 搭最小湖仓,再用 DuckLake(DuckDB + PostgreSQL)对比感受元数据架构差异。
