    湖仓一体总结

    一、架构概览

    1.1 现有离线数仓架构

    计算引擎:  Spark / Trino
资源调度:  YARN
存储格式:  Hive表（TextFile / ORC / Parquet 目录结构）
元数据:    Hive Metastore（基于 MySQL）
底层存储:  HDFS

    核心特征：全链路T+1，数据以Hive表形式存储在HDFS上

    1.2 逐步迁移湖仓架构

    计算引擎:  Spark / Trino / Flink
资源调度:  YARN
存储格式:  Apache Iceberg（ACID、快照、Schema 演进）
元数据:    Hive Metastore（基于 MySQL）
底层存储:  HDFS

    1.3 目标湖仓一体架构

    计算引擎:  Spark / Flink / Trino（多引擎共享同一份数据）
表格式:    Apache Iceberg（ACID、快照、Schema 演进）
元数据:    Polaris Catalog（统一 REST Catalog，多引擎联邦）
底层存储:  MinIO（S3 兼容对象存储，存算分离）

    二、现有离线数仓的痛点

    • 数据时效性查，T + 1瓶颈明显
      • 离线链路以小时级/天级批处理为主
    • Hive表格式的结构性缺陷
      • 更新删除代价高，修改一行数据需要重写整个分区
      • 分区模型僵化，分区是物理目录结构，按天分区后想按小时查询、变更分区粒度都要重建表
    • 小文件问题
      • 写入产生大量小文件，NameNode 压力大、查询性能骤降
    • Schema 演进困难
      • 加列、改列类型在不同引擎间行为不一致，容易读出脏数据
    • 无快照隔离
    • 无法 Time Travel
      • 误删/误写后数据无法回溯，只能靠备份恢复
    • 元数据管理瓶颈
      • 表/分区元数据与实际文件靠约定维持一致
      • Spark与Trino对Hive元数据的缓存策略不同，经常出现"一边改了另一边看不到"的一致性问题
    • 数据冗余与孤岛
      • 同一份数据在不同团队、不同集群间反复拷贝，存储浪费且口径不一
    • 存储与计算耦合
      • HDFS 存算一体，扩容存储必须同时扩容DataNode机器，资源利用率低

    三、湖仓一体如何解决痛点

    • 快照级 ACID
      • 写提交基于乐观锁的原子元数据切换，读写互不干扰
    • 支持行级 UPDATE/DELETE/MERGE INTO（Copy-on-Write / Merge-on-Read），CDC同步可直接MERGE
    • 隐藏分区（Hidden Partitioning）
      • 分区是元数据逻辑，支持分区演进（如按天→按小时）无需重建表
    • 元数据层面管理文件清单，可结合 Compaction（重写小文件）后台治理，且查询按文件级统计信息剪枝，对小文件不如Hive 敏感
    • 完整的 Schema Evolution
      • 加列/删列/改名/改类型/调整顺序，各引擎行为一致
    • 每次提交生成不可变快照，查询固定在某个快照上，结果可复现
    • Time Travel
      • SELECT * FROM t VERSION AS OF ... 或 TIMESTAMP AS OF，秒级回滚误操作（CALL rollback_to_snapshot）
    • 对时效性的提升
      • Iceberg支持 Flink 流式写入 + 增量读取（Incremental Read），湖上数据可以做到分钟级新鲜度，批流可以共用同一张Iceberg表。逐步淘汰 Lambda 双链路，走向 Kappa/批流一体
    • 存算分离
      • 存储（MinIO 集群）与计算（Spark/Flink/Trino 集群）独立扩缩容
    • REST 接口的开放 Catalog
      • 替代 Hive Metastore 的 Thrift + MySQL 私有协议。Spark / Flink / Trino 挂载同一个 Polaris Catalog，看到同一份表元数据，一处提交、处处可见，彻底解决引擎间一致性问题
    • 批流一体
      • 一份数据、一套口径。Flink CDC 实时入湖（分钟级）+ Spark 离线批处理写同一张 Iceberg 表

    湖仓一体其他的优势：

    • 数据只存一份
      • 同一张Iceberg表同时被 Spark（ETL/ML）、Flink（实时）、Trino（交互式分析/BI）直接访问，消除跨引擎、跨团队的数据拷贝
    • 数据版本化
      • 快照天然带来"类 Git"能力
    • 更强的数据治理能力
      • 统一 Catalog 下，表级血缘、权限、审计、数据目录（Data Discovery）可以集中建设
    • 查询性能优化手段更丰富
      • 元数据级别的文件剪枝（min/max 统计 + 谓词下推）比 Hive 分区裁剪粒度细得多，支持 Z-Order / Sort / Bucket 等数据布局优化，点查和范围查询可跳过 90%+ 文件。快照隔离使 Trino 等引擎可以安全地做元数据缓存，进一步降低规划开销

    四、半结构化与非结构化数据的处理

    4.1 半结构化数据

    Hive体系下JSON通常以STRING类型整列存储，查询时用get_json_object解析，问题是慢、无类型、无校验、无法下推过滤

    湖仓方案：

    • 原生嵌套类型：Iceberg 完整支持 STRUCT / LIST / MAP 复杂类型，JSON 日志可建模为强类型嵌套列，Trino/Spark 可直接点查子字段（event.user.id），并享受列式存储的裁剪与压缩
    • Schema 演进适配字段漂移：日志/事件字段频繁增删，Iceberg的Schema Evolution允许JSON字段平滑增减，无需重建表
    • 半结构化仍可选择性保留 JSON 字符串：对极度多变的字段可保留原始 JSON 列兜底，冷热字段分离建模，兼顾灵活性与性能
    • 格式统一：原始 JSON/Avro 数据入湖后统一转 Parquet/ORC 列存，压缩率和查询性能提升数倍，同时保留原始快照可回溯

    4.2 非结构化数据：对象存储即天然载体

    非结构化数据在HDFS体系下，只能另建文件存储，与分析链路完全割裂

    湖仓方案：

    • MinIO 天然就是文件存储：非结构化文件（图片/PDF/音视频/模型产物）直接以对象形式存放，享受纠删码、版本控制、生命周期管理
    • "元数据入表、文件入桶"模式：用 Iceberg 表管理非结构化文件的元数据（路径、标签、业务属性、向量索引地址），通过 SQL 即可检索文件
    • AI/ML 场景打通：
      • 训练框架（PyTorch/TF）通过 S3 协议直接流式读取 MinIO，无需数据搬迁
      • 结合 Iceberg 快照实现训练数据集版本化（可复现的实验）
      • 可向多模态湖仓演进：非结构化数据 + 嵌入向量 + 结构化标签统一管理，支撑 RAG、特征平台等场景
    • 一份存储，两份用途：同一份文件既服务于分析引擎，也服务于 AI 训练，消除"数据湖"与"AI 存储"的重复建设

    五、总结

    维度 现有离线数仓 (HDFS+YARN+Hive) 湖仓一体 (Polaris+MinIO+Iceberg)
    数据时效 T+1 / 小时级 分钟级（流式入湖 + 增量计算）
    数据更新 重写分区 行级 ACID MERGE
    存算架构 耦合、3 副本 分离、纠删码 ~1.4x
    弹性能力 固定资源、潮汐浪费 按需扩缩容
    元数据 Hive Metastore 瓶颈、引擎不一致 Polaris 统一 REST Catalog、强一致
    半结构化 STRING + 运行时解析 原生嵌套类型 + Schema 演进
    非结构化 体系外另建存储 元数据入表 + 文件入桶，AI 直通
    数据治理 分散、血缘难追 统一 Catalog、快照版本化
    生态 绑定 Hive 协议 开放标准，多引擎即插即用

    结论 本次改造以Iceberg表格式为核心解决ACID、时效性与 Schema演进问题，以MinIO存算分离解决成本与弹性问题，以Polaris统一Catalog解决一致性与治理问题，最终实现一份数据、多引擎共享、批流一体、面向分析与AI双重负载的现代数据底座
